# 「ある人生」人生シミュレータ — コーディングエージェント引き継ぎ仕様書

- 文書版: 1.0 / 2026-10-17
- 現行実装: `life-simulator-v17/index.html` (v1.7)
- 言語: 日本語
- ステータス: **現行コードを確認した事実**と**合意済みの目標仕様**、**未実装・不具合の疑い**を明示的に区別する。
- 最優先: 現行の動作を壊さず、イベントの相関と選択結果の納得感を向上させる。

## 0. エージェントへの最初の指示

1. 同梱 `index.html` を必ず読んでから変更する。現行のイベント名、関数名、状態フィールドを憶測で置き換えない。
2. 最初に **現行挙動を再現する自動テスト**を作る。特に「1年間の複数イベント」「選択待ち」「同時交際」「セーブ・ロード」「相手ID」「成人条件」を優先する。
3. UIの見た目より、`state`・`engine`・`events`・`render` の責務分離を優先してよい。ただし単一HTMLでオフライン実行できる配布物を維持する。
4. 変更のたびに構文チェックとブラウザ操作テストを実施。構文チェックだけで完成と判定しない。
5. 旧バージョンのセーブデータは**移行不要**。バージョンが異なる場合は通知せず破棄して新しい人生を開始する。**同一バージョン内の保存・再開は必須**。
6. 成人向けの性的・親密な経験は同意・関係性・結果を区別する。未成年期は思春期、身体の変化、感情、対人関係を非露骨に扱う。

## 1. 製品概要・体験

日本で生まれ育つ女性主人公の誕生から死までを追う、ローカル完結型の人生シミュレータ。参考となるのは1in8b.lifeの「人生の時間経過と選択」の構造であり、複製ではない。主人公は自律的に行動し、ユーザーは **自動進行** と **選択介入** を切り替える。選択介入では毎年複数の選択イベントが起こり得る。入学・卒業など、選択のない節目も記録する。人生の記録には、結果の変化量と、一部の感情的な出来事に限った折りたたみ式「日記を見る」を付ける。

**プロダクト原則**: 「正解の人生」は作らない。性格、指向、羞恥、性的欲求、道徳観、交際形態、子どもの有無によって一律の幸福・不幸を決めない。イベントは利得と負担の両方を持ち、過去の経験が将来の選択肢・発生条件・結果に反映される。

## 2. 実行・配布条件

- HTML + CSS + Vanilla JavaScript。現行は**単一の `index.html`**、外部サーバ・API・CDNなしで `file://` から開けること。
- 日本語UI。デスクトップは一画面で概観できるコンパクトな三カラム構成を目指す。モバイルでも横スクロールを強制しない。
- 擬似乱数をシードで固定し、同じ初期状態・同じ選択なら同じ結果になること。
- 保存はブラウザ `localStorage`。現行キーは `life-simulator-v17`。新バージョンでは新しいキーを使い、旧キーを黙って削除する。
- 保存・読込時に `rngState`、未処理イベント、選択待ち、NPCのIDと状態を失わない。
- ローカルJSのキーワード/ルールによる自由入力は将来的に拡張可。LLM同等の自然言語理解を謳わない。

## 3. 時間進行・イベントキュー【重要】

### 3.1 現行の流れ

`step()` → 年齢を1増やす → 身体/生活の年次更新 → 自動節目 `lifeMilestones()` → NPC関係 `advanceBonds()` → `pickYearEvents()` → `processYearEvents()` → `settle()` → 記録・表示。

- 年初に候補を抽選し、当年のイベントIDを `state.yearEvents` に保持する。
- `processYearEvents()` はイベントを順に処理。選択介入モードでは `state.pending` を立てて**その場で停止**。選択後、**年齢を増やさず**次の同年イベントを提示。
- 「10年進める」も未解決の選択があればそこで止まる。未処理キューを破棄しない。
- 自動モードでは選択肢を抽選し、自動確定して次へ進む。
- 複数交際に関する特別選択は `pending='multiple_relationship'`、`pendingBondId` で処理。
- イベント確定時には、選択結果・状態差分・日記・相手関係の変化を記録。

### 3.2 合意済みの年間発生密度

| 年齢 | 年間イベント上限（子・孫による加算前） | 抽選係数（現行） |
|---|---:|---:|
| 0–5 | 1 | 0.30 |
| 6–9 | 2 | 0.58 |
| 10–14 | 3 | 0.82 |
| 15–35 | 6 | 1.35 |
| 36–49 | 5 | 1.05 |
| 50–64 | 4 | 0.85 |
| 65–79 | 3 | 0.70 |
| 80+ | 2 | 0.55 |

子どもがいれば+1枠、孫がいればさらに+1枠。最大8件。ただし**現行の子・孫の実体モデルは未完成**。子・孫の追加イベントは、実在する家族エンティティを基に発生させること。

15–49歳でパートナーがいないとき、出会い系イベントの抽選確率を増やす: 15–35歳 ×2.1、36–49歳 ×1.6。パートナーがいる場合は増幅しない。上限を超えないよう最終確率を0–1にクランプする。

### 3.3 改善要件

- 現行は候補抽選後にシャッフルし上限で切る。重要イベントが埋もれないよう、`priority`、`cooldown`、`chain`、`weight`、`mutexGroup`、`maxPerYear` をデータ定義へ追加する。
- **必須イベント**（卒業、出産後の節目等）と **抽選イベント** は分離する。
- 同年内に状態が変化した場合、後続イベントの発生条件を再評価する。現行は一部を再評価するが、確定済みの抽選候補が消える問題や新たな候補を補充する仕様は明確化が必要。
- `pending` が存在する間は年齢を進めない。自動処理の途中で重要選択が発生した場合の動作を明示する。
- 再開後に同じイベントを二重適用しない。イベントキューはシリアライズ可能なID/インスタンス形式で保持する。

## 4. 主人公のデータモデル

### 4.1 状態値と隠し資質

**平均0**。誕生時の状態値は概ね `-10…+10`。個人ごとに不可視の変動範囲（資質）を持つ。基準範囲は `-50…+50`、資質の偏りで `-30…+70` などになる。通常は偏り±20程度、稀に±30〜40程度。絶対値90に近い範囲は極端で希少。

**重要**: 資質によって上限が+70なら**現在値+70まで到達し、+50超もUIに表示**する。下限-70も同様。資質の上下限は非公開だが、極端な現在値からプレイヤーが推測することは許容する。値を±50で表示上クランプしてはいけない。

現在コード: `traitBounds()`、`bounded()`、`initialValue()`。資質範囲は現行 `[-50+shift,50+shift]`。`shift` は通常約±20、まれに±30/±40。

### 4.2 主な状態パラメータ

| 内部キー | UI名 | 意味・設計上の注意 |
|---|---|---|
| `health` | 健康 | 心身の健康状態。加齢や疾病で変動 |
| `happiness` | 満足度 | 直近の生活満足感。人生全体の「正解」ではない |
| `knowledge` | 知識 | 知識・学習蓄積。学歴とは別 |
| `social` | 社交性 | 交流のしやすさ・行動傾向 |
| `stress` | ストレス | 高いほど負担。単純な「高い=良い」評価をしない |
| `money` | 経済余裕 | 生活の余裕。現金残高そのものではない |
| `independence` | 自立性 | 自分で意思決定する傾向 |
| `selfUnderstanding` | 自己理解 | 自分の考えや希望への理解。性的自己理解と重複要検討 |
| `aesthetics` | 美意識 | 美・装い・感性を重視する傾向 |
| `morality` | 道徳心 | 社会規範・自分の倫理観を重視する傾向。低値=犯罪者とはしない |
| `trust` | 信頼（旧） | 主人公全体の値は曖昧。**相手別の `bond.trust` に移行推奨** |
| `secrecy` | 秘密（旧） | 単一スコアではなく秘密のエンティティ化推奨 |

性・親密さの関連値（現行 `state.sexuality`）: `desire` 性的欲求、`initiative` 積極性、`shyness` 羞恥度、`curiosity` 好奇心、`selfKnowledge` 性的自己理解、`selfAcceptance` 自己肯定感、`boundaryVoice` 意思表明力、`intimacyNeed` 親密さ欲求。`maturity` は身体的成熟の別尺度（現行0–100）であり、**同意能力の判定や性的イベント解禁に単独使用しない**。指向 `orientation` は別属性。性的欲求の高さ、指向、交際の有無、満足度を混同しない。

### 4.3 状態・性格・関係の責務分離（次期設計）

- **資質**: 非公開の上下限、比較的固定。
- **性格傾向**: 社交性、積極性、羞恥、道徳観、美意識等。徐々に変化。
- **状態**: 健康、ストレス、生活満足度、経済余裕等。状況で変化。
- **知識・経験**: 知識、自己理解、経験フラグ/履歴。蓄積・再解釈。
- **関係別**: 愛情、信頼、同意、約束、秘密、関係の状態は `bondId` 単位。
- 重複した抽象パラメータを増やしすぎない。UIは主要指標を中心に、性・親密さは折りたたみ。

## 5. 選択結果と数値バランス

### 5.1 合意済みルール

- 通常の選択: **プラスとマイナス両方**の影響を持つ。各主要パラメータの変動は原則 `-3…+3`、合計は概ね `+1`。
- 例: 新しい友達と仲良くする → 満足度+1、社交性+2、知識-1、自立性-1（合計+1）。
- 転機イベント（引っ越し・一人暮らし・就職/失業・結婚/離別・病気等）は最大±10程度。例: 一人暮らし開始 → 経済余裕-10、自立性+2。
- ユーザーが明示指定した特別効果は優先: **友達の経験談 → 性的欲求+10**、**未成年飲酒を実行 → 道徳心-10**。
- 「プラス/マイナス」は数値の符号であり、道徳的評価とは区別。ストレス-2は良い方向の可能性がある。
- 数値が資質上限/下限に到達したら実変動が小さくなる。記録には**実際の変化量**を表示する。

### 5.2 現行実装の限界と改善

現行 `balancedChoiceEffect()` は、イベントの指定効果に後付けでパラメータを追加・補正して合計+1を目指す。このため、文脈に合わない変化（例: 勉強していないのに知識-1）が混ざり得る。**今後はイベント定義の段階で意味のあるトレードオフを明記**し、実行時のバランサーは検証/例外検知に限定すること。性的パラメータは別経路 `sexualEffects` で適用され、合計+1ルールの対象外になり得る点も仕様化する。

## 6. NPC・交際・親密さ

### 6.1 人物識別

各NPCに一意の `bondId`（現行 `bond_1` など）。名前は表示用であり、**名前で同一人物判定しない**。同姓同名は存在し得る。性別と名前候補は整合させる（過去に男性名「健太」が女性NPCに付いた不具合があった）。人物の性別、恋愛/性的指向、欲求、名前は概念的に別。

NPCモデル（現行）: `id`、`name`、`gender`、`status`、`affection`、`trust`、`openness`、`consent`、その他 `normalizeBond()` による特性。関係状態: `acquaintance` 知人、`close` 親しい人、`partner` 交際中、`former` 元交際相手。

### 6.2 関係の進行

- 自動進行中にも出会い、親交、交際、親密な経験、別れが起こり得る。
- 交際成立や身体的な親密さは本人・相手の意思を別々に評価する。相手の拒否を尊重し、ユーザーの選択だけで強制成立させない。
- **すでにパートナーがいる状態で別の交際を開始する場合は重要イベントとして停止**。既存交際を優先 / 交際を終了して新しい相手へ / 関係者全員の合意による複数交際 / 秘密の交際、という異なる分岐を持つ。
- 複数交際は自動的に増殖させない。合意の有無、秘密、嫉妬、発覚、再交渉、関係修復などの連鎖イベントへ接続する。
- 交際相手ごとに、性的欲求、積極性、羞恥、相性、親密さの希望、合意の更新履歴を持たせるのが目標。

### 6.3 性的・親密な経験履歴

`state.sexuality.experience[]` に `id`、`age`、`kind`、`description`、`partnerId`、`consent`、`mutual`、`satisfaction`、`emotionalImpact`、`private`、`relationshipStatus` を保持する。性的経験の数だけで人格を評価しない。初デート、初キス、初めての成人同士の性的経験、対話、拒絶、別れ、再会などは別種の履歴とフラグで管理する。初回経験は**同じ人生で一度だけ**発生させる。年齢・双方の意思・相手の存在など条件を満たすこと。

現行は経験履歴を最大200件、人生の記録を最大400件に制限している。全履歴保持が必要か、アーカイブ方式を設計すること。

### 6.4 年齢と表現

- 15–17歳の恋愛、告白、街での声掛け、身体への関心は**非露骨**に扱う。
- 成人向けの身体的親密さの経験イベントは18歳以上かつ相互の自由な意思を必要条件とする。
- 身体的成熟、性的欲求、性的指向、同意能力、法律上の年齢条件を分離する。
- 同意は継続的で撤回可能。拒否・境界線の表明がゲーム上の失敗や罰にならないようにする。
- 性的・恋愛的な喜び、対話、自己発見、互いの尊重を積極的に描き、葛藤や不倫だけに偏らない。

## 7. イベント定義と発生条件

### 7.1 現行形式（実コードに合わせた概要）

```js
{
  id: 'positive_date_idea',
  min: 18, max: 75, p: 0.19,
  title: '二人で楽しい時間を計画',
  text: '交際相手と、二人が楽しめる休日の過ごし方を考えた。',
  requires: s => hasPartner(s),
  choices: [
    ['少し特別なデートを企画する', { happiness: 2, money: -2, social: 1 }],
    // ...
  ],
  outcomes: ['shared_activity', 'mutual_talk', 'shared_activity'],
  context: 'partner'
}
```

現行の主要フィールド: `id`、`min`、`max`、`p`、`once`、`title`、`text`、`choices`、`requires`、`context`、`outcomes`、`sexualEffects`、`locationKind`、`major`。追加予定: `priority`、`tags`、`cooldownYears`、`prerequisites`、`excludes`、`followUps`、`effects` の型付き表現。

### 7.2 発生条件の整理【最重要改善】

現行 `needsPartner()` は**選択肢の文言を正規表現で検査**してパートナー必須を推定している。これは暫定策であり誤検知・漏れがある。次期仕様では **`requires` を機械可読な条件で明示**し、文言に依存しないこと。

例:

```js
eligibility: {
  minAge: 18,
  maxAge: 75,
  partner: 'required',      // required | absent | any
  relationshipStatus: ['partner'],
  firstKiss: 'any',
  cooldownYears: 3,
  oncePerLife: false
}
```

- 「パートナーと相談する」「交際相手と話す」「二人で決める」等の選択肢を持つイベントは、**交際相手がいる場合のみ**発生する。
- パートナー不要の選択肢と必要な選択肢が混在する場合、イベント自体を分割するか、選択肢単位の `requires` を使う。
- `outcome` が対象とするNPCは「最初に見つかった交際相手」ではなく**明示的な `targetBondId`**で固定する。
- `first_date` → `first_kiss` → `first_intimacy` は絶対的な一本道にせず、経験の有無が後続の発生率や日記を変える相関を作る。
- 選択イベントの結果は、即時パラメータ変化に加え、数年後のイベント解禁・確率変化・関係変化へ接続する。

## 8. 人生の記録と日記

### 8.1 記録すべきもの

- **選択イベント**: 年齢、タイトル、選択肢、実際のパラメータ差分、人物関係の変化、該当すれば日記。
- **自動イベント**: 入学、卒業、就職、初経、更年期の変化、65歳の節目、出会い、交際開始、別れ、転居、死亡など。選択肢がなくても記録する。
- **重要な経験**: 初デート、初キス、成人の性的経験、複数交際の開始・合意・秘密の発覚など。人物IDと紐づける。
- 1年間に複数件発生しても、同年齢の複数行として正しい順序で表示する。

### 8.2 日記仕様

- 全件に付けず、節目・感情が大きく動く出来事に限定。
- 記録の**行の下に折りたたまれた「日記を見る」**を配置。開くと主人公の一人称で短い感想を表示。
- 年齢に応じて語彙・語り口・関心を変える。例: 子どもは短い素直な言葉、思春期は戸惑い、若年成人は期待と不安、中年期は生活の文脈、高齢期は回想。ただし年齢による決めつけは避ける。
- 同じイベントでも主人公の性格、満足度、ストレス、相手への信頼、過去の経験、選択結果によって感想が変わるのが目標。
- 現行 `ageDiary()` は年齢帯ごとの定型接頭辞/結語を付ける簡易実装。**定型句の単純連結から、文脈を持つテンプレート群へ改善**する。
- UI再描画時に折りたたみ開閉状態を可能な限り維持する。

### 8.3 選択の結果を見せる

- 記録行に「結果」欄を表示し、例 `満足度+1 / 社交性+2 / 知識-1 / 自立性-1`。
- NPCの交際開始・終了、秘密、初回経験の成立/不成立など、数値以外の結果も明示。
- 「選択した」ことと「実際に成立した」ことを区別する。相手が同意しなければ成立しない。
- 即時結果だけでなく、**数年後に過去の選択が影響したことを伝える**。例: 「以前の話し合いがきっかけで…」。イベント間の因果を記録する `causedByEventId` 等を推奨。

## 9. 居住地モデル

現行 `state.location`: `region`、`terrain`、`district`、`sinceAge`、`history`。

- 地方12区分: 北海道、東北、北関東、南関東、甲信越、北陸、東海、近畿、中国、四国、九州、沖縄。
- 地形/環境6区分: 都市部、郊外、平野部、山間部、海辺、離島。
- 街区7区分: 住宅街、繁華街、商業地域、農村集落、工業地域、高所得地域、経済的困難が多い地域。
- **「居住地変更」は折りたたみUI**。通常は現在の居住地のみ見せる。
- 転居履歴を記録し、進学、就職、家族、医療、交通、生活費、出会い等の確率に影響させる。
- 将来は出生地・育った地域・現在の居住地を区別する。地域の「貧困」等を性格・道徳の決めつけに使わず、教育機会、就業、交通、医療などの環境指標に分解する。

## 10. UI仕様

- 左: 人物の基本情報、主要パラメータ、性・親密さ（折りたたみ）、人間関係（折りたたみ）、性的・親密な経験（折りたたみ）、居住地変更（折りたたみ）。
- 中央: 年齢・進行操作（1年/10年）、自動/選択介入、現在のイベント、選択肢、自由入力アクション（現行機能に従う）。
- 右: 時系列の人生記録、結果、折りたたみ日記。
- 数値は0基準で符号付き表示。±50を超える値も正確に表示する。資質の上下限は表示しない。
- 性的経験履歴は独立した折りたたみパネル。件数、年齢、種類、相手の名前とID、同意・満足・秘密等の情報を表示する（存在する項目のみ）。
- 再描画でスクロール位置、開閉状態、選択待ち状態を失わない。

## 11. 保存・再現性

- 保存対象: 主人公の全状態、資質、性的属性、NPC全員、人物IDカウンタ、経験履歴、イベント発生履歴、年齢、現在のイベント、未処理キュー、乱数状態、居住地履歴、日記、フラグ。
- 保存/読込後に、選択待ちの同じイベント・同じ選択肢が表示される。
- 同じシードと同じ介入列は、同じ人生記録と数値を再現する。
- 異なる版のセーブデータは通知なしで破棄。旧版互換処理は実装しない。
- データ削除は**アプリ専用キーのみ**。他アプリの `localStorage` は消さない。

## 12. 現行コードから判明した技術的課題・リスク

1. **年齢別密度は実装されているが、候補イベント数と抽選確率に強く依存**。上限に達する保証はない。分布を大量シミュレーションで測る。
2. **`needsPartner()` は文言ベース**。`requires` による明示条件へ置き換える。
3. **`handleSocialOutcome()` は対象NPCとして先頭のパートナー等を選ぶ**。複数交際時に意図しない相手の履歴が更新され得る。イベントインスタンスへ `targetBondId` を保存する。
4. **`balancedChoiceEffect()` は自動的に無関係な値を増減させ得る**。イベント設計時に意味のある効果を定義する。
5. **資質の数値とUIメーターの目盛が一致しているか要確認**。表示文字列は±50を超えるが、メーターの換算は現行 `(+90)/1.8`。
6. **子・孫の実体モデルが不足**。`flags.hasChildren` / `flags.hasGrandchildren` を参照するだけではイベントが増えない。
7. **`state`、乱数、DOMが密結合**。ロジック単体テストのため分離が必要。
8. **NPC関係は主人公の0基準±50と異なる既存0–100スケール**。別尺度であることを仕様に明記するか、段階的に統一する。
9. **`sexuality.maturity` は0–100**。本人の性格指標の0基準スケールと混同しない。
10. **未成年飲酒の年齢は15–19歳**。ユーザーの「15〜20」は境界が曖昧。日本の20歳未満禁止に合わせ、20歳は含めない現行実装を維持するのが妥当。
11. **`friends_story` は `once:true`**。性的欲求+10は通常イベントの±3例外である。選択肢どちらでも適用される現行挙動を明示的に検証する。
12. **初回イベントや相互同意の条件**を実コードで精査すること。イベント名だけで成立条件を推定しない。
13. **既存の実装にはブラウザ長期進行テストの完了記録がない**。現行を安定版と決めつけず、先に実測する。
14. **主人公の健康や経済余裕などの数値が年次処理で大きく増減する**。選択イベントのバランスとは別に、年間自然変動の調整が必要。
15. **自由入力の解釈は辞書/正規表現ベース**。予期しない行為を成立させず、意図と結果を区別する。

## 15. 開発の優先順位

**P0 — 正しさと安定性**: エンジン/UI分離、イベントキュー、対象NPC ID、発生条件、セーブ・ロード、年齢・同意条件、回帰テスト。
